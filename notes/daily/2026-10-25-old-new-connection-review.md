# 旧版与新版 Codex 通路复核

## 结论

Git 暂存区旧版与新版采用相同的核心协议：本机 Codex App Server、JSON-RPC、每次请求创建临时线程并在结束后关闭连接。旧版没有常驻连接复用或独立的快速翻译协议。当前证据不足以通过恢复这份旧连接器重现用户曾体验到的速度。

用户本轮反馈已从连接失败更新为连接成功、速度慢。历史快速体验作为有效反馈保留；当前暂存区快照在现有环境不能完成相同请求，无法还原其历史速度。

## 逐步核对

| 环节 | 暂存区旧版 | 当前新版 |
| --- | --- | --- |
| 程序选择 | PATH 首个有效入口，npm 入口转 codex.js | PATH 首个有效入口，Windows npm 安装解析到同一安装内的原生程序 |
| 启动 | 每次 spawn codex app-server | 每次 spawn codex app-server |
| 初始化 | initialize → initialized；check 中 account/read | 相同 |
| 请求 | config/read → thread/start → turn/start | 相同 |
| 线程 | ephemeral:true；sessions Map 写入后删除，没有读取复用 | ephemeral:true；本地历史转为请求上下文 |
| 接收与结束 | agentMessage/delta；turn/completed 后关闭进程 | 同样接收流；补充完整消息兜底、重连提示与空回答检查 |
| 模型与思考 | 继承 Codex 配置 | 模型继承；翻译局部 low，其余继承 |
| 网络环境 | 继承父进程环境，不读取 Windows 系统代理 | 保留显式代理；缺省使用 Electron 解析的系统路由 |
| 翻译输入 | JSON selection + conversation，翻译要求放在对话消息内 | 翻译要求 + JSON selection/history/question，含不执行资料内指令的约束 |
| 外部依赖 | Codex 路由不调用 MCP、浏览器自动化或直接模型 API；账户由 CLI 处理 | 相同；助手不新增 API Key 输入 |

旧版另有独立可选 ApiProvider，经 API Key 请求 /chat/completions；它与上述 Codex 通路不同。未读取用户旧加密设置，无法判断历史快速体验当时选择的来源。

## 本轮实测

旧源码每次直接由 git show :src/providers/codex.ts 读取并编译到忽略的临时目录；没有恢复工作区或修改暂存区。两者使用同一 npm Codex 安装、同一隔离工作目录、同一公开短句 The sky is blue.，均提供当前系统代理。为消除网络差异，对旧版的代理注入只发生在测试启动器中，不算旧版原有能力。

交替顺序为旧、新、旧、新：

| 通路 | 两次结果 | 失败阶段或耗时 |
| --- | --- | --- |
| 原样旧连接器 | 登录检查完成；生成失败 | thread/start 两次 -32600，错误分类 invalid transport；约 1.03、0.99 秒即失败 |
| 当前新版 | 两次均收到天空是蓝色的。 | 包含登录检查总耗时约 8.91、8.80 秒；首字约 8.38、8.61 秒；无重连 |

另在临时旧副本中仅改变禁用配置键的引用方式，单次约 5 秒后进程断开；没有得到可用方案，未把实验参数加入产品。invalid transport 的具体配置根因尚未确认。

以上测试验证连接器，不代表真实 Chrome、微信、WPS 的划词、点击、窗口链路已验收。测试脚本在 .runtime/click-diagnostic/old-new-compare.cjs，不读取真实选区、聊天或凭据。

## 复用判断与后续路线

- 可直接保留：Codex JSON-RPC 协议、文本流接收、账户检查、临时线程策略。
- 需要改造：Windows 子进程隐藏、系统代理、可定位的错误反馈、流中断处理；不能用登录成功代替生成验收。
- 不直接恢复：旧版连接器整体；原样请求当前失败，且没有可复现的速度优势。
- 保持当前产品路线，本轮不修改生产代码、不切换模型服务、不打包。先建立真实使用样本的首字/完成耗时与失败率基线，再决定是否接受 Codex 的延迟。若要求接近即时翻译，独立评估专用翻译通路；服务费用、API Key 及数据处理范围应在选型后确认，不承诺未经测试的速度。

主要风险是网络及服务波动、模型设置变化、隔离环境与实际启动环境差异，以及历史快速版本的具体运行配置尚未复现。不能据此将所有延迟归因于 Codex 服务，也不能把重新启动进程认定为主要耗时。
