# 拾句工具条位置与显示等待修复

日期：2026-10-26。用户反馈驱动的本地修复，不推送、不发布。

## 已确认反馈与范围

用户确认 Chrome、微信、WPS 都能触发工具条，问题是显示较慢，微信/WPS 的工具条出现在左上角。由此将三个应用的“可触发”记录为用户实测证据；完整问答、准确位置和触发耗时仍分别验收。

本轮修正坐标选择和反复加载窗口的开销，保留同一工作区内前一轮语言重译修复。模型来源、配置、依赖、应用版本号、已有 release 资产不变。

## 根因与具体改动

1. `src/main/desktop.ts` 原先无条件优先使用 `event.endBottom`，仅排除非数值和 -99999。已安装 selection-hook 的 `src/windows/core/types.h:112-119` 将文字边界初始化为 (0,0)；其 `src/windows/core/worker.cc:358-379` 在仅取得鼠标位置时使用 MouseSingle/MouseDual（posLevel 1/2）。这种事件能有正文，但文字矩形并不存在，因此旧逻辑把默认原点误当作文字位置。与用户左上角表现一致；尚未采集用户应用的真实事件，不宣称每个现场事件均已确认是同一取词方法。
2. 新增 `src/main/selection-anchor.ts`：posLevel 3/4 且文字边界有效、非退化时优先文字终点；否则使用有效的事件 mousePosEnd；最后才取当前鼠标。物理像素只转 DIP 一次，允许多屏负坐标及合法零坐标；不按应用名硬编码。
3. 原先 `showToolbar` 每次销毁并新建 BrowserWindow、loadFile，且 500ms 回调可能在工具条已经不需要显示时再次显示。现在启动隐藏预加载，后续事件只定位、更新状态和显示；外部点击、复制、Escape/关闭及打开结果窗只隐藏工具条。
4. ready 与 wanted 状态共同控制显示，捕获具体窗口身份，等待期间的新选区使用最新位置；收起后就绪不会复活工具条。页面异常退出则销毁，下次划词再创建；退出应用仍销毁所有窗口。复用后新选区会清除工具条遗留提示，避免旧复制反馈挡住三个按钮。

坐标回归证明代码路径纠正；预加载回归证明不再每次创建/加载，但二者不等于现场取词总耗时已量化。UIA、IAccessible、剪贴板回退本身的等待尚未测量，没有修改第三方原生库、关闭安全回退或虚报提速数字。

## 试用办法与验收

本地目录版位于 `.runtime/toolbar-fix/win-unpacked/`，入口为其中的 `拾句.exe`，需保留整个目录一起使用，不能只复制 EXE。程序内容归档共 209 项，已核对包含坐标/窗口复用和上一轮语言重译修复，未打入 history.json、preferences.json、model-key.enc 或 .runtime 资料。程序启动仍沿用拾句原有用户数据目录；仅在用户自行运行时读取已有配置，本轮工具未读取该目录。

便携单文件未完成：首次缺 Electron 下载，改用项目已安装的 electronDist；接着缺 winCodeSign 下载，改用已有 `.runtime/builder-cache`；随后目录版资源处理完成，但 makensis.exe 启动报 spawn UNKNOWN。没有改仓库打包配置、签名要求或发布流程来掩盖失败，不声称生成了可分发的单文件包；目录版也尚未完成本机启动验收。

原有 release/0.2.0-alpha.2 的两份 EXE 与 SHA256SUMS.txt 共 3 个文件哈希前后相同。当前本地目录版 EXE 的哈希和检查摘要保存在 `.runtime/toolbar-fix/local-verification.json`，不作为正式发布校验清单。

1. Chrome、微信、WPS 各在专门公开文本中划词：先测第一下，再连续 3 次。记录“松开鼠标 → 工具条出现”的体感/录屏时延，和工具条是否位于选区或松手附近。
2. 微信/WPS 的坐标未知时应随本次松手位置，而不是左上角或取词完成后已经移动的鼠标位置。拖选相同文本、反向拖选、双击分别验证。
3. 靠近屏幕四边和副显示器再测，确保工具条可见、按钮可点；多屏与混合缩放需真实环境验证。
4. 工具条还未显示就点外部，应保持收起；重复划词、复制、打开问 AI 后应正常重现，不显示上一次的提示。
5. 如仍感觉慢，下一轮按“松手 → 取词事件到达 → 工具条可见”分段采样。当前修复只去除了重复窗口加载，不把剩余等待归因给模型。

## 后续显示回归与修正

用户反馈 toolbar-fix 版反而无法触发，并明确有托盘图标、复制公开文字后快捷键也不显示。由此优先排查两个入口共用的显示链路，而不是将问题归为微信/WPS 兼容性。

### 可复现缺口与修正

缓存工具条仅在 ready-to-show 回调置为 ready。若页面 loadFile 已完成但首次绘制通知未到，`revealToolbar` 永远返回，快捷键和自动取词都会卡住。这是代码和新增回归测试确认的失败路径；没有捕获用户现场事件，不能断言已证实现场仅由某一个原生事件缺失引起。上一轮测试主动发 ready-to-show，未覆盖完成加载而不触发首次绘制的情况。

本轮先将测试窗口的 loadFile 改为可延迟完成，再增加两项：完成加载但没有 ready-to-show 仍能显示（修正前失败）；选区已收起后加载完成仍保持隐藏。现在 loadFile fulfilled 和 ready-to-show 都进入 `markToolbarReady`，共用窗口身份、销毁、ready 去重及 wanted 收起保护；两者迟到或重复都不应重新弹窗。
