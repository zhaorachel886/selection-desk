# 开发与发布流程整理

> 执行方式：按 executing-plans 顺序完成，每步核验后继续。

**目标：** 日常开发在项目根目录完成，旧版独立归档，发布通过手动触发的 GitHub Actions 完成。

**约束：** 保留旧版源码和原始索引；不修改产品行为，不读取真实问答和凭据，不覆盖已发布 v0.2.0-alpha.2 的资产，不新增自动发布触发器。

## 步骤

1. 将原暂存区原始索引、文件清单、源码 ZIP 与可读取的本地 Git 归档引用保存到 `.local-archive/`；逐文件核验 ZIP 与原 Git blob 一致。
2. 获取远程 main，将根目录本地 main 与 upstream 建立正常关联；只更新 Git 引用与索引，保留全部工作区文件。将本地截图和归档排除在后续提交之外。
3. 安装包附件改用 Shiju ASCII 名，输出目录随版本变化。保留手动发布，文档明确提交与发布两步；本机检查推送认证状态，连接器作为已验证的备用提交通路。
4. 检查 Git 状态、归档引用、产品源码与已发布版本的差异；执行类型检查和测试。提交本轮流程改动并核对远端；不触发新版本发布。

## 验证依据

- 原索引 SHA256 已保存，源码 ZIP 的 53 个文件与原 Git blob 逐一相同。
- main 已关联 origin/main；产品 src 无改动，归档和本地截图已排除在提交之外。
- 类型检查与 56 项测试通过。真实 ASCII 附件安装版、便携版构建成功，两份哈希与校验清单独立核对一致；错误附件集合被拒绝。
- 手动工作流解析检查通过，默认 publish=false，仅 main 可发布。6 个本地 Git 标签场景通过，覆盖标签缺失、轻量与附注标签、标签冲突、非法输入和远程不可读；审查复核通过。
